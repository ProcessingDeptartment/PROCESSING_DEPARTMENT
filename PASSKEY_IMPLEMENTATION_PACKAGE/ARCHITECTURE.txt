TIER 2: NETWORK (HTTP REST API)
──────────────────────────────────
  /api/auth/passkey/
  ├─ register-options ........... GET cert options
  ├─ register-verify ............ Store credential
  ├─ authenticate-options ....... GET signing challenge
  └─ authenticate-verify ........ Verify signature

  All requests include:
  • username (who is signing)
  • challenge (one-time random)
  • credential data (encrypted)

┌─────────────────────────────────────────────────────────────────────────────┐
│                       PASSKEY REGISTRATION FLOW                             │
└─────────────────────────────────────────────────────────────────────────────┘

USER CLICKS "REGISTER PASSKEY"
  │
  ├─→ passkey-auth.js:registerPasskey()
  │
  ├─→ 1. GET OPTIONS
  │   └─→ POST /api/auth/passkey/register-options
  │       ├─→ generateRegistrationOptions()
  │       ├─→ Challenge = random 32 bytes
  │       ├─→ Store in PasskeyChallenge table (10 min TTL)
  │       └─→ Return to client
  │
  ├─→ 2. BROWSER PROMPT
  │   └─→ "Create a passkey?"
  │       User chooses:
  │       ├─ Biometric (fingerprint, face)
  │       ├─ PIN/Password
  │       └─ Security key
  │
  ├─→ 3. AUTHENTICATOR GENERATES
  │   └─→ Key Pair
  │       ├─ Public Key (shared with server)
  │       └─ Private Key (stays on device)
  │
  ├─→ 4. CLIENT SENDS ATTESTATION
  │   └─→ POST /api/auth/passkey/register-verify
  │       Body: {
  │         username: "user@abagold.co.za",
  │         id: "base64url-credential-id",
  │         response: {
  │           clientDataJSON: "...",
  │           attestationObject: "..."
  │         }
  │       }
  │
  ├─→ 5. SERVER VERIFIES
  │   └─→ verifyRegistrationResponse()
  │       ├─ Check challenge used matches (prevents replay)
  │       ├─ Validate attestation cert
  │       ├─ Extract public key from credential
  │       ├─ Verify signed data authentic
  │       └─ VERIFIED ✓
  │
  ├─→ 6. STORE CREDENTIAL
  │   └─→ INSERT INTO UserPasskey
  │       ├─ id = "base64url-credential-id"
  │       ├─ publicKey = "extracted-public-key"
  │       ├─ signCount = 0 (clone detection baseline)
  │       ├─ createdAt = NOW()
  │       └─ username = "user@abagold.co.za"
  │
  └─→ 7. SUCCESS
      └─→ "Passkey registered successfully ✓"


┌─────────────────────────────────────────────────────────────────────────────┐
│                     PASSKEY VERIFICATION SIGNING FLOW                       │
└─────────────────────────────────────────────────────────────────────────────┘

USER FILLS VERIFICATION FORM & CLICKS "🔐 SIGN WITH PASSKEY"
  │
  ├─→ passkey-auth.js:authenticateWithPasskey()
  │
  ├─→ 1. GET OPTIONS
  │   └─→ POST /api/auth/passkey/authenticate-options
  │       ├─→ Lookup UserPasskey for user
  │       ├─→ generateAuthenticationOptions()
  │       ├─→ Challenge = random 32 bytes
  │       ├─→ Store in PasskeyChallenge table (10 min TTL)
  │       ├─→ List allowed credentials (user's passkeys)
  │       └─→ Return to client
  │
  ├─→ 2. BROWSER PROMPT
  │   └─→ "Unlock with [device type]?"
  │       User completes:
  │       ├─ Biometric verification (fingerprint/face)
  │       ├─ PIN entry
  │       └─ Device checks permission
  │
  ├─→ 3. AUTHENTICATOR SIGNS
  │   └─→ signature = SIGN(challenge, private_key)
  │       ├─ Private key never leaves device
  │       ├─ Signs specific challenge with crypto algorithm
  │       ├─ Returns: {signature, authenticatorData}
  │       └─ signCount++ (increment for clone detection)
  │
  ├─→ 4. CLIENT SENDS ASSERTION
  │   └─→ POST /api/auth/passkey/authenticate-verify
  │       Body: {
  │         username: "user@abagold.co.za",
  │         id: "base64url-credential-id",
  │         response: {
  │           clientDataJSON: "...",
  │           authenticatorData: "...",
  │           signature: "base64url-signature"
  │         }
  │       }
  │
  ├─→ 5. SERVER VERIFIES SIGNATURE
  │   └─→ verifyAuthenticationResponse()
  │       ├─ Lookup credential in UserPasskey
  │       ├─ Get stored publicKey for this credential
  │       ├─ VERIFY(signature, challenge, publicKey)
  │       │  └─ If invalid → REJECT (wrong device/tampering)
  │       ├─ Check signCount increased (clone detection)
  │       │  └─ If decreased → ALERT (possible clone!)
  │       └─ VERIFIED ✓
  │
  ├─→ 6. LOG VERIFICATION
  │   └─→ INSERT INTO PasskeySignature
  │       ├─ recordKey = "cans-produced" (which form)
  │       ├─ verifiedBy = "john.smith@abagold.co.za"
  │       ├─ verifiedDate = "2026-10-01"
  │       ├─ credentialId = credential used
  │       ├─ signatureValue = signature (stored)
  │       ├─ verified = true
  │       ├─ entryIds = [entries signed]
  │       └─ loggedAt = NOW()
  │
  ├─→ 7. RETURN CREDENTIAL ID TO CLIENT
  │   └─→ {
  │       success: true,
  │       credentialId: "base64url-credential-id",
  │       message: "Verification signed successfully ✓"
  │     }
  │
  ├─→ 8. CLIENT STORES CREDENTIAL ID
  │   └─→ <input id="verify_signature" type="hidden"
  │           value="base64url-credential-id">
  │
  └─→ 9. USER CLICKS "LOG VERIFICATION"
      └─→ Form submitted with:
          ├─ verifiedBy: "John Smith"
          ├─ verifiedTitle: "QA Manager"
          ├─ verifiedDate: "2026-10-01"
          └─ verifiedSignature: "base64url-credential-id" ← Passkey ID, not typed text!


┌─────────────────────────────────────────────────────────────────────────────┐
│                       SECURITY THREAT PROTECTION                            │
└─────────────────────────────────────────────────────────────────────────────┘

THREAT: Phishing attack (attacker steals password)
PROTECTION:
  ❌ No passwords sent over network
  ❌ No passwords stored on device
  ✓ Private key never leaves device
  ✓ Can't log in without biometric/PIN

THREAT: Signature forgery (attacker copies signature)
PROTECTION:
  ✓ Each signature is cryptographically unique
  ✓ Tied to specific challenge (can't reuse)
  ✓ Verification fails if challenge/signature mismatch
  ✓ Algorithm: ECDSA/RSA makes math impossible to forge

THREAT: Replay attack (attacker replays old signature)
PROTECTION:
  ✓ Each challenge is random and unique
  ✓ Challenge marked "used" after verification
  ✓ Expired challenges (10 min TTL) rejected
  ✓ Server checks challenge matches signature

THREAT: Device cloning (attacker copies authenticator)
PROTECTION:
  ✓ Sign counter increments with each signature
  ✓ If counter decreases → possible clone detected
  ✓ Server can revoke cloned credential
  ✓ User can register new passkey

THREAT: Man-in-the-middle (attacker intercepts traffic)
PROTECTION:
  ✓ Use HTTPS/TLS (encrypt all network traffic)
  ✓ Origin/RP ID validation (prevents wrong site)
  ✓ Challenge prevents tampering with signature
  ✓ Signature verification detects modifications

THREAT: Weak password (attacker brute forces)
PROTECTION:
  ✓ No passwords used (cryptographic keys instead)
  ✓ Device locks after failed biometric attempts
  ✓ 256-bit entropy from key generation
  ✓ Impossible to brute force

┌─────────────────────────────────────────────────────────────────────────────┐
│                          CREDENTIAL STORAGE                                 │
└─────────────────────────────────────────────────────────────────────────────┘

ON DEVICE (Authenticator - Secure Storage):
─────────────────────────────────────────────
  [Encrypted Secure Storage]
  ├─ Private Key (never leaves device)
  │  └─ Used to sign verification challenges
  ├─ Public Key (sent to server once)
  │  └─ Server stores for verification
  └─ Sign Counter
     └─ Incremented with each signature (clone detection)

ON SERVER (Database):
─────────────────────
  UserPasskey table:
  ├─ Public Key (only)
  │  └─ Used to verify signatures from device
  ├─ Credential ID
  │  └─ Identifier for this passkey
  ├─ Sign Counter
  │  └─ Expected value (should match or increase)
  └─ Metadata
     └─ Device type, last used, etc

VERIFICATION_LOG (Legacy, kept for audit trail):
─────────────────────────────────────────────────
  KeyValue table:
  ├─ verification_log:record-key
  │  └─ JSON array of old typed signatures (archived)

PASSKEY_SIGNATURE (New, passkey audit trail):
───────────────────────────────────────────────
  PasskeySignature table:
  ├─ Record of each passkey signature
  ├─ Who signed (verifiedBy)
  ├─ When (verifiedDate, loggedAt)
  ├─ Which credential (credentialId)
  ├─ Signature value (for verification)
  └─ Whether verified successfully


┌─────────────────────────────────────────────────────────────────────────────┐
│                        KEY COMPONENTS & RESPONSIBILITIES                    │
└─────────────────────────────────────────────────────────────────────────────┘

passkey-auth.js (CLIENT)
  Responsibility: Handle WebAuthn ceremony
  Does:
    ✓ Get options from server
    ✓ Interact with browser's WebAuthn API
    ✓ Handle user's authenticator (biometric/PIN)
    ✓ Send attestation/assertion to server
    ✓ Manage errors and UI

signoff-block.js (CLIENT)
  Responsibility: Signature field UI
  Does:
    ✓ Replace typed signature input with passkey button
    ✓ Call PasskeyAuth when button clicked
    ✓ Store credential ID returned
    ✓ Display signing history

passkey-api-endpoints.js (SERVER)
  Responsibility: WebAuthn server-side logic
  Does:
    ✓ Generate options for client
    ✓ Verify attestation/assertion responses
    ✓ Extract and store credentials
    ✓ Log signatures
    ✓ Provide verification results

UserPasskey (DATABASE)
  Responsibility: Store registered credentials
  Contains:
    ✓ Public key (for verification)
    ✓ Credential ID
    ✓ Sign count (clone detection)
    ✓ Authenticator metadata

PasskeyChallenge (DATABASE)
  Responsibility: Prevent replay attacks
  Contains:
    ✓ Random challenge (unique per ceremony)
    ✓ Used/unused flag
    ✓ Expiration (10 min TTL)
    ✓ Purpose (registration vs auth)

PasskeySignature (DATABASE)
  Responsibility: Audit trail of signing
  Contains:
    ✓ Record of who signed what when
    ✓ Signature value (for non-repudiation)
    ✓ Whether verification succeeded
    ✓ Error messages if failed
