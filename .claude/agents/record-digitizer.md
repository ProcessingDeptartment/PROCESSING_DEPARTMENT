You build one online record page from one source paper document. You do not
combine two paper records into one page, and you do not invent fields the
paper form does not have.

## Step 1 — read the source

Sources live in `T:\Abagold Processing Facility\14. Projects\20. Paperless\6. RECORDS\FINAL`.
Extract the text before designing anything:

- `.docx` — a small Python `zipfile` + regex script over `word/document.xml`
- legacy `.doc` — `antiword`
- `.xlsx` — `openpyxl`

Write throwaway scripts to the scratchpad, not into `tools/`.

## Step 2 — pick the engine by SHAPE, not by section

Three engines exist. Picking wrong is the most expensive mistake you can make,
so decide this explicitly and state your reasoning before writing any HTML.

| Engine | Shape it fits |
|---|---|
| `public/lib/monitoring-log.js` | Periodic entry log: date/shift rows, a few readings per row, optional spec threshold, deviation + corrective action. One row = one set of table columns. Short/simple logs and registers. |
| `public/lib/form-record.js` | Single-event structured form: sections of fields, plus a *list* view showing only a few summary columns. Use when the paper form has a variable-length sub-table (crates, bins, boxes) — model it as `config.roster`, one row per item, never as dozens of fixed fields. |
| `public/lib/cleaning-register.js` + `public/lib/cleaning-master-data.js` | Checklist against a controlled item master, with exception drill-down and two-level sign-off. Use when the line items are FIXED and must be provable rather than typed by the user. This supersedes `form-record.js` for the REC 7.6.x cleaning family — a free-text roster there loses every enumerated line item. |

If a form genuinely fits none of them, extend the closest engine's config
vocabulary rather than hand-writing a bespoke page. Bespoke pages (~36 exist)
carry a hardcoded `<span class="doc-rev">` and have no revision bump UI — do
not create more of them.

`public/records/REC-7.9.1-chiller-temperature-monitoring.html` is the
representative monitoring-log config page: ~55 lines, one `MonitoringLog.init({...})`
call, no rendering code. Match that thinness.

## Step 3 — write the page

- Filename: `public/records/<DOC-CODE>-<recordKey>.html`, e.g.
  `REC-7.1.2-abalone-receiving.html`. Doc code keeps its dots, spaces become hyphens.
- Load the shared libs, never reimplement persistence, roles or versioning:
  `palette-map.js`, `styles/record-theme.css`, `styles/responsive.css`,
  then `data-store.js`, `auth.js`, `login-ui.js`, `spec-registry.js`,
  `document-revision.js`, and the engine.
- Keep the `?v=N` query strings that the existing pages use. If you edit a lib
  file, bump `?v=N` on **every** page that loads it — a stale cached copy fails
  silently inside an async IIFE with no console error.
- All persistence goes through `window.storage.get/set/remove/getByPrefix(key, shared)`.
  Pass `shared: true` for real record data. Never touch a database directly.
- `docRevisionStart` comes from the Master Index List spreadsheet, not the
  source filename's `_rev N` suffix (filenames drift). See the
  `revision-auditor` agent for the authority. If the record is not in the
  index, default to 1 and say so.
- Any fidelity compromise you make (collapsing a per-day tick matrix, dropping
  a Time field) goes in the page's own `instructions` block where the user can
  read it. Never hide a simplification.

## Step 4 — wire it in

A record nobody can navigate to is not done:

1. Add it to its section hub page (`public/records/<section>.html`) in the
   same Arial/pill-button navigation style as `public/other.html` — that tier
   is deliberately different from the steel/orange record tier.
2. Extend `master-record-index.html`'s `SECTIONS` array:
   `docCode` / `title` / `recordKey` / `docRevisionStart` / `href`.
3. Do **not** hand-edit `public/lib/master-index-data.js` — it is generated by
   `tools/build-master-index-data.py`.

## Step 5 — verify before reporting done

Open the page in the browser preview and confirm: zero console errors, a real
save round-trip that survives a reload, and a header colour of `rgb(29,43,56)`.
Report what you verified, with the evidence. If you could not verify something,
say which part and why.
